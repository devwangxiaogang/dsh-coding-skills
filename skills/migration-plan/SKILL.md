# 迁移计划

迁移与重构的分界：**重构是内部结构变化，迁移是外部依赖或数据形态变化**。迁移失败通常不是代码写错，而是"旧数据/旧客户端/旧环境"没被纳入计划。

## 使用方法

**你会怎么说**
- `把 Spring Boot 2 升到 3`
- `这个库要换掉，怎么弄`
- `数据库要加个字段/改类型`
- `从 AWS 迁到别处`

**我需要什么**（缺了先问，不猜）
- 迁移对象与目标版本（依赖 / 运行时 / schema / 平台 / 协议）
- 爆炸半径：多少服务、多少数据、是否多环境、是否有离线客户端
- 停机容忍度：能否停写、能停多久、能否双跑
- 回滚要求：必须能一键回滚，还是允许"只向前"

**我会查**
```bash
<包管理器> outdated / <依赖清单>            # 版本差距
sed -n '1,80p' <上游 CHANGELOG 或 MIGRATION 指南>
grep -rn "<被移除的 API/字段>" --include=<ext>   # 本仓库命中点
git log --oneline -5 -- <构建/部署配置>
```

**产出**：见 §7——兼容矩阵 + 分阶段步骤（每阶段含回滚点与停止条件）+ 数据校验方案

**边界**：内部代码结构怎么拆，用 `refactor-plan`；本技能只管"换掉外部依赖/数据"这件事

## 1. 先判定迁移类型

| 类型 | 典型风险 | 关键动作 |
|---|---|---|
| 依赖大版本 | API 移除、默认行为变更、传递依赖冲突 | 读 breaking changes，逐个 grep 命中点 |
| 运行时/语言版本 | 语法与库不兼容、CI 镜像、生产环境 | 先升运行时再升依赖，分两次发 |
| 框架 | 生命週期/配置模型变化、扩展点消失 | 先建新骨架并行跑，再切流量 |
| 数据库 schema | 旧代码读新结构、双写不一致、锁与大表 | 加列→回填→切读→删列，四段走 |
| 平台/云 | 网络与权限模型、DNS/证书、成本 | 先影子流量，再切读，再切写 |
| 协议/序列化 | 双向兼容、版本协商 | 新旧并存期必须双向可读 |

不同类型的回滚点不一样，先归类再谈步骤。

## 2. 读上游，找命中点

- 上游 `CHANGELOG` / `MIGRATION.md` / release notes：只看 breaking 与 deprecated 两节
- 把每条 breaking change 转成一次 grep，命中的文件就是工作量清单
- 明确"上游已删但本仓库仍用"的 API，逐个替换（编译器/类型检查是最好的清单）
- 记录上游推荐路径与社区已知坑；版本目标选**最近一个稳定大版本**，不要跳两个大版本一次升

## 3. 兼容矩阵

画一张表，把"旧代码 / 新代码"与"旧数据 / 新数据 / 旧客户端 / 新客户端"的组合列全，标出：

- 哪些组合**必须同时上线**（不允许混跑）
- 哪些组合**允许短时混跑**（灰度期）
- 每个格子的验证手段

矩阵里出现"没想过"的格子，就是故障的藏身处。

## 4. 分阶段与回滚点

每个阶段必须回答：进入条件、验证方式、回滚动作、停止条件。

通用次序（按风险递增）：

1. **准备**：升运行时/工具链，不动业务代码
2. **并存**：新旧实现同时存在，新路径默认关闭（开关控制）
3. **影子**：把真实流量复制给新路径，只比对结果不返回
4. **切读**：新路径处理读，旧路径仍可写（或反之）
5. **切写**：写路径切换，保留双写一段时间
6. **清理**：确认无回退需求后删旧代码、删开关、删兼容层

**回滚必须是配置级**（开关/路由），不是"再发一次版"。任何一个阶段没写清回滚动作，就不能开始。

## 5. 数据迁移专项

- schema 变更**只做加法**：加列/加表，允许 NULL 或带默认值；改类型等于新建列 + 回填 + 切换 + 删旧列
- 回填脚本必须**幂等**、可断点续跑、限速（避免打满主库）
- 回填要有**校验查询**：条数对账、抽样比对、聚合指标（总额/最大值）前后一致
- 双写期要监控**差值**，不是只看"没报错"
- 大表操作注意锁与复制延迟，必要时分批 + 观察
- 删除旧列/旧表放在最后一个阶段，且要求"零读取"证据（监控或日志统计）

## 6. 验证

- 行为差异测试：迁移前后跑同一批输入，对比输出（golden files）
- 性能与体积回归：延迟、内存、包体/镜像大小（见 `perf-investigate`）
- 灰度期指标：错误率、延迟、业务成功率的对照
- 数据校验：对账查询结果贴进计划，不写"应该没问题"

## 7. 输出格式

```
## 结论
<一句话：可行 / 需要先补 X / 这个目标版本会卡在 Y>

## 迁移类型与爆炸半径
- 类型：<依赖/运行时/schema/平台/协议>
- 影响：<服务数、数据量、环境、离线客户端>

## 上游 breaking changes 与本仓库命中点
| 变更 | 命中位置 | 处理 |

## 兼容矩阵
| 旧代码 | 新代码 | 旧数据 | 新数据 | 能否混跑 | 验证 |

## 阶段计划
### 阶段 N: <一句话>
进入条件 / 动作 / 验证 / 回滚 / 停止条件

## 数据迁移与校验
<脚本、幂等性、限速、对账查询与期望值>

## 不做什么
<明确排除，防止范围膨胀>

## 风险清单
<按可能性×影响排序，附缓解手段>
```

## 8. 边界

- 不跳过"影子/灰度"直接全量切换，除非用户明确接受停机或不可回滚
- 不为迁移顺手做重构，两类改动混在一起就无法归因回归
- 上游文档与实测冲突时，以**实测**为准，并在计划里标注差异
- 迁移完成后仍要保留一段可观测期，不立刻删开关
