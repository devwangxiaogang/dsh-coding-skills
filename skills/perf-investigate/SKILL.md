# 性能排查

唯一纪律：**没有测量就没有优化**。所有"我觉得这里慢"的改动都必须先变成一个数字，否则你无法知道它是否有效、是否值得。

## 使用方法

**你会怎么说**
- `这个接口太慢了`
- `启动要 4 秒，能不能快点`
- `内存一直涨`
- `这段循环感觉有问题`

**我需要什么**（缺失时先问，不猜）
- 指标口径：延迟（P50/P95/P99）、吞吐、峰值内存、启动时间、包体大小——**具体到哪一个**
- 现状值与目标值（"2.3s → 1s 以内"），以及"够用"的界限
- 测量条件：数据量、并发数、硬件/机型、是否冷启动、是否含网络
- 是否允许改架构（缓存、索引、批处理），还是只能局部优化

**我会先跑**
```bash
# 基线：至少 3 次，记录中位数与离散度
time <命令>
hyperfine --warmup 3 --runs 10 '<命令>'      # 有则优先
# 定位：CPU / 分配 / IO
<语言 profiler>                               # py-spy / perf / async-profiler / --cpu-prof
# 变更归因
git log --oneline -10 && git bisect           # 是否某次提交后才变慢
```

**产出**：见 §7——一张"改前 / 改后 / 是否超出噪声"的对比表，加一句"够不够用"的结论。

**边界**：不在没有 profile 的情况下给"优化建议"清单；不为 <5% 的差异声称提升。

## 1. 先定义指标与预算

| 指标 | 怎么量 | 常见陷阱 |
|---|---|---|
| 延迟 | P50/P95/P99，分冷/热、分输入规模 | 只看均值；忽略尾延迟 |
| 吞吐 | 单位时间完成数，固定资源上限 | 测量时并发不足，压不出瓶颈 |
| 内存 | 峰值 RSS / 堆分配速率 / 常驻增长 | 只看总量不看待回收对象 |
| 启动 | 冷启动到可交互的时间 | 未清理缓存，测成热启动 |
| 包体/产物 | 压缩前后大小 | 未区分必需与可裁资源 |

没写清"哪个指标、什么条件、目标多少"就开始优化，等于在优化别的东西。

## 2. 建立可重复的基线

- **固定**：数据规模、并发、硬件、缓存状态、构建模式（debug/release 差异常常就是结论本身）
- **多次**：≥3 次，取中位数或最小值，同时记录离散度；波动大于 10% 说明条件不稳
- **记录命令**：一条能复制粘贴复现的命令，比一句"大概 2 秒"有价值得多
- **记录环境**：CPU/内存/机型、OS、运行时版本、依赖版本

基线不合格（波动大、条件不可控）时，先解决测量问题，再谈优化。

## 3. 定位热点（不猜）

顺序永远是：**测量 → 排序 → 只看头部**。

- CPU：火焰图/采样 profiler，看**自身耗时占比**最高的帧，不看调用次数
- IO：慢日志、查询耗时；是否存在 N+1、循环内 IO、缺索引
- 内存：分配热点、持有链（谁还引用着）、无界缓存/字典增长
- 并发：锁竞争、线程池饱和、串行化热点
- 冷启动：初始化顺序、同步网络/磁盘、类加载与反射扫描

**热点常常不在你怀疑的地方**——先证明，再动手。80% 的收益来自 1~2 个热点，找错地方就会做一堆无收益的改动。

## 4. 常见根因清单（按出现频率）

1. N+1 查询 / 循环内 IO（网络、磁盘、序列化）
2. 重复计算：循环里重复解析、重复正则编译、重复读配置
3. 无界缓存 / 全量加载（一次性读整个文件或表）
4. 多余拷贝：大对象多次序列化、字符串拼接产生大量临时对象
5. 锁粒度过粗 / 锁内做 IO
6. 热路径上的日志与字符串格式化（即使日志级别关闭）
7. 冷启动阶段串行初始化、可延迟的工作放在了启动路径
8. GC 压力：短命大对象、装箱、隐式分配（闭包、lambda、迭代器）

## 5. 改一处，测一次

- 一次只改一个变量，改完立刻重跑**同一套**基线
- 结果写进对比表：改前 / 改后 / 变化幅度 / 是否在噪声内
- 无提升或提升在噪声内的改动**回退**，不要留在代码里当"优化"
- 明显牺牲可读性或正确性的优化，必须写清代价与替代方案

## 6. 防止回退

- 热路径加基准测试（固定数据与阈值），CI 里跑或定期跑
- 关键指标上监控/埋点，给出版本间的对比
- 优化引入的缓存/索引要写清失效策略，否则下次故障就是它

## 7. 输出格式

```
## 结论
<一句话：够不够用 / 主要瓶颈在 X / 建议做 A 不做 B>

## 指标与条件
- 指标：<哪一个，P95/峰值内存/…>
- 条件：<数据规模、并发、硬件、冷热>
- 目标：<现状 → 期望>

## 基线
| 场景 | 中位数 | 离散度 | 命令 |

## 热点（按占比排序）
1. `<路径:行号 或 函数>` — 占 <X>% — 为什么慢：<机制>
   证据：<profile 截图/采样输出摘要>

## 改动与效果
| 改动 | 改前 | 改后 | 幅度 | 是否超出噪声 |

## 回退的尝试
- <改了什么> — 无提升（<幅度>），已回退

## 遗留风险
- <缓存失效、行为差异、仅在本机验证>
```

## 8. 边界

- 没有 profile 就不给优化清单；先补测量
- 不把"优化"变成"重写"：属于结构性改动时，交给 `refactor-plan` 分步做
- 单机单次测量不下结论；不同机器/机型的结果不可直接比较
- 优化不得改变可观测行为，除非用户明确接受（此时按破坏性变更处理）
