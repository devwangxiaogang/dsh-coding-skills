# Code review

审查的目标是**发现会让程序出错或让同事踩坑的问题**，不是展示品味。宁少勿滥：一条噪声意见会稀释十条有效意见。

## 使用方法

**你会怎么说**
- `帮我审一下还没提交的改动`
- `看看 commit 3f2a1c 有没有问题`
- `这个 PR 能合吗` / `这段代码有风险吗`

**我需要什么**（缺了先问，不猜）
- 范围：未提交 / 某个 `<sha>` / `<base>...HEAD` / PR 号 / 单个文件或片段
- 可选：关注点（安全、并发、性能、兼容性）与该模块的业务约束（谁能调用、数据量级）

**我会跑**
```bash
git status --short && git diff --stat
git diff && git diff --staged
git show <sha>
git diff <base>...HEAD
grep -rn "<被改的函数/字段名>"        # 确认调用方是否同步
```

**产出**：§4 的固定格式，结论在第一行；每条意见带 `路径:行号` + 具体后果
**边界**：只审给定范围；不自动改代码——你要"直接改"时我先只修 Blocker

## 1. 先确定审查范围

按用户指明的范围取 diff，不要自己扩大：

- 未提交改动：`git status` + `git diff`（含 `--staged`）
- 某个 commit：`git show <sha>`
- 分支对比：`git diff <base>...HEAD`
- PR：`gh pr diff <num>`
- 单文件/片段：直接读

范围超过 ~800 行时，先按文件分组，并在输出里说明"本次只深审了 X，其余为快速扫描"。

## 2. 读上下文，不要只看 diff

diff 只给出改动，判断需要周边：

- 被改函数的**调用方**（`grep` 函数名），确认签名/语义变化是否已同步
- 被改逻辑依赖的**数据来源**：空值、边界、并发、错误分支
- 同类代码的**既有写法**：与仓库约定不一致本身就是问题
- 测试：改动是否配了测试，测试是否真的能失败

## 3. 检查清单（按严重度）

**必须修（Blocker）**

- 正确性：边界条件、空/未定义、类型转换、off-by-one、整数溢出、时区/编码
- 资源：未关闭的句柄/流/事务、缺失的 `finally`/`use`/`defer`、泄漏的订阅或监听器
- 并发：共享可变状态无保护、锁顺序、await 在锁内、重复提交/幂等
- 错误处理：吞异常、catch 后继续用无效值、错误被转成成功返回
- 安全：拼接 SQL/命令/HTML、路径穿越、密钥硬编码、日志打印凭证、越权校验缺失
- 破坏性变更：接口/序列化格式/数据库列语义变化、删除的字段仍被读

**应该修（Major）**

- 性能：循环内 IO/N+1 查询、O(n²) 在大数据量上、无界缓存/无分页列表
- 可测试性：难以注入依赖、逻辑埋在 UI/命令处理里
- 兼容性：新依赖、版本约束、平台差异（尤其 Windows 路径、换行、大小写）
- 迁移：schema/配置/接口变化是否给了回滚或双写路径

**可以讨论（Minor）**

- 命名、重复代码、过长函数、注释与实现不符、死代码、魔法数字
- 与仓库风格不一致（缩进、import 顺序、错误信息语言）

**不要提**

- 纯个人偏好且仓库无约定支持的建议
- "建议加个注释"这类无信息量的意见（除非逻辑确实反直觉）
- 复述 diff 内容

## 4. 输出格式

```
## 结论
<一句话：可以合 / 修完 X 项再合 / 需要重新设计>

## 必须修
1. `<file>:<line>` — <问题>
   为什么：<会导致什么具体后果>
   建议：<最小可行改法，必要时给代码片段>

## 应该修
...

## 可以讨论
...

## 我验证过 / 没验证
- 验证过：<读过的调用方、跑过的测试、复现过的路径>
- 没验证：<只能静态推断、缺环境的部分>
```

规则：

- 每条必须带 `路径:行号`，否则读者无法定位
- "为什么"要写具体后果（"并发下会写坏文件"），不写"不规范"
- 建议给最小改法；重构级建议单独列出并说明代价
- 不确定的地方明确标"未验证"，不要伪装成结论

## 5. 边界

- 只审查给的改动；发现范围外的问题，单独列"顺手发现（未改动）"
- 不替用户提交、不自动改代码，除非用户要求
- 用户要求"直接改"时，先只修 Blocker，再问是否继续
