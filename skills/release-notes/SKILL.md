# 发版说明

输出只描述**本区间内真实发生过的改动**。先取提交与 diff 统计，再写文字；不编造、不夸大、不漏破坏性变更。

## 使用方法

**你会怎么说**
- `准备发版，写一下更新说明`
- `写 changelog` / `这个版本号该定多少`
- `从 v1.4.0 到现在的改动整理一下`

**我需要什么**（缺了先问，不猜）
- 区间：上一个 tag（不给就自己 `git describe` 取）与目标版本
- 受众：最终用户 / 集成方 / 内部团队（决定详略与措辞）
- 已知风险：是否包含数据库/协议/配置变更

**我会跑**
```bash
git describe --tags --abbrev=0
git log --oneline <last>..HEAD
git diff --stat <last>..HEAD
git diff <last>..HEAD -- package.json
```

**产出**：§4 模板 + 开头的版本判定与理由；破坏性变更必须写清"变了什么/谁受影响/怎么升级"
**边界**：只写文件，不 `git tag`、不 push，除非你明确要求

## 1. 取事实

```bash
git describe --tags --abbrev=0          # 上一个 tag
git log --oneline <last>..HEAD          # 区间内提交
git log --format='%h %s' --no-merges <last>..HEAD
git diff --stat <last>..HEAD            # 规模
git diff <last>..HEAD -- package.json   # 依赖变化（按仓库调整路径）
```

再抽查关键提交的 diff，确认提交信息与实际改动一致——提交信息写错时以 diff 为准。

## 2. 语义化版本判定

| 区间内存在 | 版本动作 |
|---|---|
| 任何破坏性变更（删字段/改签名/改默认行为/最低运行时版本提高） | **major**（0.x 阶段用 minor，并在说明中标注 breaking） |
| 新能力、新技能、新端点 | **minor** |
| 仅修复、文档、内部重构、依赖补丁 | **patch** |

判定写在说明开头，并给一句理由。无法判定时列出候选与各自的代价，让用户决定。

## 3. 破坏性变更必须写清三件事

1. **变了什么**：旧行为 → 新行为，带代码对比
2. **谁受影响**：调用方/配置文件/已存数据/下游集成
3. **怎么升级**：可执行的步骤或迁移脚本；能否回滚

只写"有破坏性变更"而不写升级方式，等于没写。

## 4. 输出模板

```markdown
# v<X.Y.Z> — <YYYY-MM-DD>

<一句话概括这个版本的主题>

## 破坏性变更
- **<项>**：<旧 → 新>。影响：<范围>。升级：<步骤>

## 新增
- <能力描述，讲用户能做什么，不列文件名>

## 修复
- <现象 → 原因 → 现在的结果>

## 性能 / 体积
- <指标：改前 → 改后，测试条件>

## 依赖与兼容性
- 依赖：<升级/新增/移除及原因>
- 最低支持：<运行时/平台版本变化>

## 升级方式
1. <命令或配置改动>

## 已知问题
- <未解决项与规避方式；没有则写"无">
```

## 5. 写作规则

- 按**用户可感知的行为**分组，不按提交顺序罗列；同类提交合并成一条
- 一条变更一行，能一句话说清就不用两句
- 修复类写"现象 + 原因"，不写"修复了 bug"
- 内部重构、CI、格式化：合并成一条"内部改进"，不占篇幅
- 链接到相关 issue/PR（`#123`），便于追溯
- 不写"全面优化"、"大幅提升"这类无法证伪的措辞，要给数字

## 6. 本仓库（dsh skill bundle）的特有检查

发布 skill bundle 时额外确认：

- `package.json` 的 `version` 与 tag 一致，`files` 包含 `cordis.patch.yml` 与 `skills`
- 新增/删除的 skill 在说明里点名（用户靠名字调用）
- `locale/*.json` 的描述与实际技能数一致
- 安装验证：`plugin_manager install_bundle` 用 `github:<owner>/<repo>#v<X.Y.Z>` 装一遍，确认技能出现在会话目录

## 7. 边界

- 只写文件，不执行 `git tag` / push，除非用户明确要求
- 区间内提交信息与 diff 冲突时，以 diff 为准并在输出中标注
- 不确定是否算破坏性变更时，**按破坏性处理**并在说明中标注存疑
