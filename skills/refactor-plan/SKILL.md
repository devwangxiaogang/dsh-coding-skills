# 重构计划

重构的定义：**外部行为不变，内部结构改变**。如果一个步骤会改变行为，它不是重构，要单独拆成功能改动——混在一起就无法判断回归是结构问题还是逻辑问题。

## 1. 先写清三件事

1. **目标**：要解决的具体痛点（"每次加字段要改 5 个文件"），不是"代码不优雅"
2. **不动点**：哪些对外契约必须保持不变——函数签名、序列化格式、数据库列、HTTP 响应、CLI 参数
3. **完成判据**：可观测的终态（"删除 A/B 两个旧实现，全仓库仅剩 C 一条路径"）

目标写不出可观测判据时，说明还没想清楚，不要开工。

## 2. 建立基线（没有基线就没有"没坏"）

- 现有测试跑一遍，记录：通过数、失败数、耗时
- 覆盖不到的关键路径：先补**特征测试**（characterization test）——固定当前行为，哪怕当前行为是错的
- 记录性能基线（如果重构涉及热路径）：P50/P95、内存、启动时间
- 记录代码规模：目标文件行数、圈复杂度（可选）

基线不绿就动手 = 后面无法区分"我改坏的"和"本来就坏的"。

## 3. 拆分原则

每个步骤必须同时满足：

| 要求 | 含义 |
|---|---|
| 可独立合并 | 单独进主干不破坏任何东西，不必等后续步骤 |
| 可独立回滚 | 出问题能 revert 这一步，不影响前后 |
| 行为可验证 | 有对应的测试或手动路径，能证明"没变" |
| 规模可控 | 单步 diff 一次看得完（经验值 ≤ 300 行） |

拆分优先顺序（风险从低到高）：

1. **加**：先加新实现/新字段，新旧并存（不改调用方）
2. **迁**：逐个把调用方切到新路径，每切一批提交一次
3. **删**：确认无调用方后删旧实现（用 grep/编译期报错证明，不靠记忆）
4. **收**：清理临时开关、兼容层、注释掉的旧代码

**禁止**：一步之内既改结构又改行为；一次提交里混入格式化。

## 4. 步骤模板

每一步写成这样，写不出"验证"的那步就是没设计好：

```
### Step N: <一句话动作>
改动：<文件/符号列表，谁被谁替代>
不改：<明确列出这次不碰的东西>
验证：<命令 + 期望结果；或手动路径>
回滚：<revert 即可 / 需要额外操作：如数据兼容>
风险：<可能踩到的地方>
```

## 5. 迁移类改动的额外要求

- 双写/双读期：写新读旧 → 写新读新 → 停写旧 → 删旧，共 4 段，每段能独立观察
- 数据变更必须可回滚或向前兼容：新增字段允许 NULL、默认值先落库再切读
- 对外 API：先加新端点，标记旧端点 deprecated，给出版本窗口后再删
- 配置/开关：新路径要有独立开关，能在不回滚代码的情况下关掉

## 6. 输出格式

```
## 现状
<痛点 + 证据：行数、重复次数、改动成本>

## 目标与不动点
...

## 基线
- 测试：X passed / Y failed
- 补齐的特征测试：<列出>
- 性能：...

## 计划
Step 1 ... Step N（按上面的模板）

## 不做什么
<明确排除的范围，防止后期膨胀>

## 停止条件
<出现什么情况就停手回头（如基线测试连续失败、diff 超预期 2 倍）>
```

## 7. 边界

- 用户只问"怎么改"时，只给计划，不动代码
- 执行中每完成一步，重跑基线；基线变红立即定位，不要继续下一步
- 发现"顺手能改好的"问题，单独列出，不塞进本次重构
