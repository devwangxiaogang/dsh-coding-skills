# 接口设计

接口一旦有人调用就是**契约**。改契约的成本永远高于一开始想清楚：调用方数量只会增加，不会减少。

## 使用方法

**你会怎么说**
- `帮我设计这个接口`
- `这个 API 有什么问题`
- `错误码该怎么定` / `分页用 offset 还是 cursor`
- `这个字段能删吗` / `要不要升 v2`

**我需要什么**（缺了先问，不猜）
- 调用方：内部服务 / 第三方集成 / 公开 SDK（决定兼容承诺的强度）
- 兼容承诺：能否破坏、Deprecation 窗口多长、是否已有客户端在线上
- 数据形状：单条还是列表、规模量级、是否会分页、有无强一致要求
- 谁消费错误：人看日志、程序重试、还是 UI 直接展示

**我会查**
```bash
grep -rn "<现有接口路径或方法名>" --include=<ext>     # 现有调用方数量
git log --oneline -10 -- <接口/契约文件>
ls openapi* schema* api* 2>/dev/null                  # 是否已有契约文件
```

**产出**：见 §7——契约草案（请求/响应/错误/分页）+ 兼容性判定 + 不能做的地方

**边界**：不擅自破坏已有字段语义；实现细节（内部类、私有方法）不在此技能范围

## 1. 先定三件事

1. **谁调用**：内部两个服务之间可以粗暴演进；公开 SDK 的每个字段都是永久负债
2. **兼容承诺**：多久内不能破坏？升级窗口如何通知？没有答案时按"一年内不可破坏"设计
3. **失败如何被消费**：可重试 / 需人工 / 需展示给用户——决定错误结构的信息密度

## 2. 命名与形状

- 资源用**名词复数**：`/orders/{id}/items`，动作交给 HTTP 方法
- 一个接口只做一件事；`doEverything` 式参数（一堆可选开关）是设计的逃逸
- 参数语义一致：`limit` 到处是同义；不要一个接口 `pageSize`、另一个 `count`
- 时间统一 ISO 8601 + 显式时区（`2026-01-01T00:00:00Z`），不传本地时间串
- 金额用整数最小单位 + 币种，不用浮点
- ID 用不透明字符串，别让调用方解析结构；自增数字 ID 会泄漏规模且难迁移
- 布尔参数改用枚举或独立接口（`?archived=true|false|all` 优于两个布尔位）

## 3. 输入校验

- 必填 / 可选 / 默认值在契约里写清，不要靠实现隐式决定
- **未知字段的策略要明确**：严格模式拒绝（防拼写错误）还是宽松忽略（利于演进）——两种都对，但必须一致
- 上限写死：字符串长度、数组长度、分页大小、请求体大小
- 幂等：创建类接口支持幂等键（`Idempotency-Key`）或天然幂等 ID
- 校验失败要指出**哪个字段、期望什么**，不要只返回"参数错误"

## 4. 输出与错误

统一错误结构，一次定好，永远不要出现两种：

```json
{
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "订单不存在",
    "details": [{ "field": "id", "reason": "not_found" }],
    "requestId": "req_8f2a"
  }
}
```

- `code` 是**机器可判定的稳定字符串**，`message` 可以改文案；不要用 message 做分支
- HTTP 状态表达类别（4xx 客户端 / 5xx 服务端），业务 `code` 表达细节
- 不把内部异常、堆栈、SQL、上游原始报文透给调用方；写进日志用 `requestId` 关联
- **可重试性要显式**：`retryable: true|false`，或约定哪些 code 可重试
- 分页统一：大数据量用 cursor（`nextCursor`），小数据且需要跳页才用 offset；两者别混用
- 空结果与不存在区分：列表返回 `[]`，单资源不存在返回 404，不要都返回 `null`

## 5. 兼容与演进

| 变更 | 是否破坏 | 做法 |
|---|---|---|
| 新增可选字段 / 新增接口 | 否 | 直接加，文档标注版本 |
| 新增枚举值 | **可能** | 要求客户端容忍未知值；否则按破坏处理 |
| 字段改类型 / 改单位 / 改时区语义 | 是 | 新字段并行，旧字段保留到窗口结束 |
| 删除字段 | 是 | 先 deprecate + 监控零调用，再删 |
| 改默认行为（分页大小、排序） | 是 | 视为破坏性变更 |
| 改错误 code 字符串 | 是 | 调用方在分支上 |

规则：**只加不改**；需要改就加新版本（`/v2` 或新字段），旧路径给一个明确的 sunset 日期。

契约文件（OpenAPI / JSON Schema / 类型定义）是**唯一事实源**；手写文档与生成物不得同时存在两套。

## 6. 评审时的重点

- 这个接口 3 年后还能扩展吗（加字段、加维度、加权限）
- 调用方能否只凭响应区分"没数据"和"没权限"
- 一次列表请求的最坏代价是否可控（无界查询、N+1、深分页）
- 权限模型是否说清：谁能调、能看谁的资源
- 是否有"调试用"参数泄漏到正式契约（`?debug=1`、`?skipAuth`）

## 7. 输出格式

```
## 结论
<一句话：可以定稿 / 建议改 X / 这个设计会锁死扩展>

## 契约草案
- 路径与方法：
- 请求：<字段、类型、必填、默认值、上限>
- 响应：<结构、分页方式>
- 错误：<code 列表 + 可重试性>

## 兼容性判定
<这次是新增还是破坏；破坏时给演进路径与窗口>

## 必须修 / 建议改
1. `<项>` — 问题：<后果>  改法：<最小改动>

## 我不确定
<需要调用方信息才能定的点>
```

## 8. 边界

- 只给契约与判定，不替用户写实现（除非要求）
- 不为了"优雅"引入调用方无法承担的复杂度；先看调用方能力
- 已有线上契约时，默认按"不可破坏"处理，破坏必须先说明迁移成本
